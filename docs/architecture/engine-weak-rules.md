# GeoSpace Weak — Simulation Engine Rules

This document records the simulation rules agreed for the **GeoSpace Weak** engine.
It is the canonical location for engine behavior decisions. The
[decision log](../DECISIONS.md) summarizes them; the
[engine status](backend-and-engine-status.md) tracks what is implemented.

> **Evidence status:** Sections marked **Accepted** were explicitly approved by
> the user in a design review held on 2026-11-17 and 2026-11-18
> (America/Sao_Paulo). Sections marked **Proposed** await approval. Sections
> marked **Open** have not been discussed. **Nothing in this document is
> implemented or verified yet.**

## 0. Scope and principles — Accepted

| Rule | Detail |
| --- | --- |
| Weak is the test bed for Mid | Weak validates the engine, time rules and travel modes in a topological world before Mid adds geographic geometry. |
| Weak is self-sufficient | Distances come from the graph itself (curated edge lengths). Mid is a fidelity upgrade, not a prerequisite. |
| Extension points, not dependencies | Mid will relate to separate apps (money, items/clothing, status bar). The core exposes extension points for them and depends on none. None are built now. |
| The engine stores facts only | A character's *beliefs* live in the LLM. The engine delivers only what is **physically observable** at the moment of observation. |
| One canonical state, several projections | The frontend `WorldSnapshot` and the LLM context envelope are separate projections of the same canonical state. |
| Engine stack | **TypeScript on Node.js.** Persistence, deployment and the database remain open. |

## 1. Time, asynchronous mode and economy mode — Accepted

### 1.1 Time policy

- **D1 — Simulated time runs 1:1 with real time.** The world continues while
  the user is away. The companion's calendar paces time.
- This is the **time policy**. **On-demand chronological advancement** remains
  the **execution strategy** hypothesis: the engine does not tick every minute;
  it advances from the last checkpoint to the requested instant when a query or
  command arrives. The causal properties in the
  [engine status](backend-and-engine-status.md#32-on-demand-chronological-advancement-working-hypothesis)
  still have to be verified.

### 1.2 Deterministic autopilot

**D2** — When no decision is made (economy mode, platform API failure, interval
between scheduled checks), a deterministic autopilot applies, with no LLM call
and no token cost. Priority order:

1. An active journey completes according to physics.
2. A calendar commitment is attended.
3. A still-valid declared plan is followed.
4. A routine pattern applies (for example, end of work leads home).
5. Otherwise, the character stays where it is.

Economy mode disables *creativity* (new outings), not *physics* or *obligations*.

### 1.3 Forward-only decisions

**D3** — Asynchronous queries to the character ask about the **future**, never
the past ("it is 14:00, you are at X, these are your options: what will you do
next and until when?"). The answer becomes a **plan with a deadline** that the
engine validates and schedules.

- **The past is never rewritten.** Retroactive co-presence cannot occur.
- An invalid or missing answer falls back to the autopilot.

### 1.4 Commitments

```ts
interface Commitment {
  id: string;
  placeId: PlaceId;
  startsAt: Instant;
  endsAt: Instant;
  source: "platform_calendar" | "companion" | "user";
  status: "scheduled" | "en_route" | "attended" | "late" | "missed" | "declined";
}
```

- `late`: arrived after the start; the delay is recorded.
- `missed`: did not leave in time. A consequence of physics.
- `declined`: explicitly chose not to attend through an action. A character decision.
- The engine computes a **latest departure time** (route duration, waits and a
  margin) and includes it in the projected state, for example: "commitment at
  15:00 at B; to arrive on time from here, leave by 14:20".
  - In live conversation, if the character does not leave, it is late.
  - The autopilot leaves at the latest departure time by default.
- The companion sees commitments **up to one week ahead**.
- In the future the companion may create and edit commitments
  (`source: "companion"`). **Only future commitments may be created or changed**;
  started or past commitments are immutable.
- `source` names the provider generically; the Kindroid calendar is reached only
  through the platform adapter.

### 1.5 Period summaries

**D4** — When live conversation resumes, the engine supplies a summary of the
period the user was away.

- **Summaries are generated by code from the event log, not by an LLM.** An
  optional LLM prose layer may come later, never as a source of truth.
- **Hierarchical roll-up:** events → daily summary → weekly summary.
  Routine collapses ("Mon–Fri: regular work routine"); **exceptions are
  promoted** (missed or declined commitment, new place, co-presence with the
  user, large delay).
- **Injection budget on resume:** the last ~24 hours in detail, the previous
  days of the current week as daily summaries, earlier weeks as weekly summaries
  up to about one month. Beyond that, only anchors (home, work, familiar places).

## 2. Durations and travel modes — Accepted

| # | Rule |
| --- | --- |
| D5 | The **actual trip uses the duration of the chosen mode**. A **weighted average across modes** (weights from the character's mobility profile) is the **typical travel time** between places, used for nearby context, autopilot estimates and display ("about 15 min away"). |
| D6 | **Weak:** every edge has a curated `lengthM`. Defaults come from the edge type and district profile and are overridden where it matters. The distance between any two places is the **shortest path in the graph**. **Mid:** lengths are computed from the real map. The duration computation is the same in both stages. Validation **warns** (does not reject) on inconsistent lengths, such as triangle-inequality violations. |
| D7 | **Taxi and ride-hailing use the shortest path over road-accessible edges.** A **taxi** departs from a fixed **taxi stand** node; the number of stands depends on the district profile (centre > inner ring > periphery). **Ride-hailing** comes to the character; its wait depends on the district profile. Values are calibrated in a table per city size (small, medium, large, metropolis). |
| D8 | **Bus and metro:** each line has a **frequency per time band** and fixed departure times derived from it; the wait is the time until the next departure. **Random waits** (ride-hailing) are **drawn once, at departure**, with the seed recorded in the event. The **latest departure time uses a pessimistic wait** (for example, the 90th percentile). |
| D9 | **Internal unit: seconds.** Every edge has a duration **greater than zero**. The frontend converts to minutes for display only. |
| D10 | A **mobility profile** replaces money for now: allowed modes, owned vehicle, preferences. The engine offers only allowed modes with their durations; the **LLM chooses** in live conversation and the **profile decides** under autopilot. **Running** is limited (short segments, or only when late for a commitment). |
| — | Every edge declares its **allowed modes** (a park path is walk-only; an avenue allows car, ride-hailing and bus). |
| — | **Future money extension point:** the engine validates the trip, the money app approves or vetoes, the engine confirms. |

```ts
interface MobilityProfile {
  modes: readonly TravelMode[];
  ownedVehicleId: VehicleId | null;
  preference: Partial<Record<TravelMode, number>>;
}
```

## 3. Multi-leg journeys — Accepted

```ts
interface Journey {
  id: string;
  mode: TravelMode;
  status: "active" | "completed" | "cancelled";
  participants: readonly CharacterId[];
  vehicleId?: VehicleId;
  origin: PlaceId;
  destination: PlaceId;
  legs: readonly Leg[];
}

interface Leg {
  kind: "walk" | "run" | "wait" | "ride";
  from: PlaceId;
  to: PlaceId;        // equal to `from` for "wait"
  departAt: Instant;  // seconds; fixed after departure
  arriveAt: Instant;
  lineId?: string;
}
```

| # | Rule |
| --- | --- |
| D11 | The **whole itinerary is computed at departure** and fixed afterwards, except for cancellation or diversion. **The current position is not stored**; it derives from the clock. Each leg makes direction explicit. **Bus and metro in Weak:** a direct `ride` leg with no exposed intermediate stops; duration = direct time × the line's **route delay factor** (may vary by district) + a fixed time per intermediate stop. The frontend shows only the total. |
| D12 | **Waiting at a stop means being at a place**, so co-presence is possible there. Boarding ends that co-presence; each person continues separately. **Chance encounter:** the same line and the same departure give `CO_PRESENT_IN_TRANSIT` for the shared segment, without "Go Together". This requires a **relative time offset per stop** on each line. |
| D13 | **Passing through is not visiting.** Passing a place only lifts the fog ("I am near the bakery"). It creates no visit, habit or visit familiarity. Only arrival at the final destination emits `ARRIVAL_CONFIRMED`. |
| D14 | **Interruption starts from a point inside an edge** (*d* metres from X, *L − d* from Y). Walking, running, car or motorcycle: turning back costs the distance covered. Taxi or ride-hailing: alight at the next node. During `wait`: give up from the stop. **In Weak, a bus or metro `ride` leg cannot be interrupted.** A diversion is a cancellation followed by a new journey from the current point. |
| D15 | **Buildings with an interior graph** (the companion's home, the user's home): the trip starts in the actual room and walks the rooms to the entrance. **Without an interior graph, or with an unknown room:** a fixed exit time applies (for example, 1 min for a house, 3 min for a large building), starting at the entrance. |
| — | **Crossing a room occupied by the other person** emits a brief encounter event (`PASSED_BY`). In live conversation the LLM may stop there, cancelling or postponing the journey. |
| — | **Every interior graph has an entrance node** linked to its urban place; validation ensures every room is reachable from it. |
| — | Arriving at a closed place or without a key ends the journey **at the door** (details in item 9). |

## 4. User avatar — Accepted

| # | Rule |
| --- | --- |
| D16 | The user's marker is the **user's avatar in the simulation**. It is the engine's truth and **does not expire**. The user may use it to deceive in role-play (say "I am home" while placing the avatar at a bar). *Rejected: marker expiry (TTL).* |
| D17 | **`CO_PRESENT_IDLE`:** the avatar is at the place, but the user is offline. The character treats the user as asleep, busy or quiet and **must not narrate the user's actions or speech**. It becomes `CO_PRESENT` when the user resumes the conversation. |
| D18 | **The user moves only through simulated journeys**, under the same clock. **No teleporting.** The user has a **mobility profile** with the same rules as the companion, including the running limit. *Rejected: a declarative "I am here" action.* |
| — | **No omniscience:** the companion learns the truth only through physics. Example: she reaches his home and observes "he is not here"; he returns from the bar and she observes "he came in through the door, from the street". The lie unravels without the engine revealing anything. |

**Proposed defaults (no objection raised):**

- The avatar may be placed freely **only at initial setup** or through a
  **logged administrative correction**, never during a co-presence.
- **"User active"** means the frontend is open or a message was sent within the
  last N minutes. N is to be calibrated and depends on what the platform
  adapter can observe.

### Co-presence regimes

| Regime | Condition |
| --- | --- |
| `CO_PRESENT` | Same place and same room, user active |
| `CO_PRESENT_IDLE` | Same place and same room, user offline |
| `CO_PRESENT_IN_TRANSIT` | Same journey ("Go Together") **or** the same scheduled vehicle during the shared segment |
| `SAME_PLACE_DIFFERENT_ROOM` | Same building, different rooms |
| `REMOTE_WAITING` | One person reached the meeting point and waits for the other |
| `REMOTE_ONLY` | Different places or separate journeys |
| `PASSED_BY` (event) | Brief encounter when crossing an occupied room |

## 5. Provisional places and merge — Proposed

Scope: places, rooms and interior graphs.

| # | Proposal |
| --- | --- |
| D19 | **Resolve before creating.** (1) **IDs first:** the context given to the character lists places with identifiers, and actions carry the ID. (2) Only for mentions outside that list, a **four-layer heuristic search:** normalization and exact match → alias table (grows with each merge) → fuzzy name match above a threshold → tie-break by graph proximity and category. (3) **Generic mention** ("going to the bakery"): the nearest known place of that category; otherwise a provisional place. (4) **When uncertain:** create the provisional place and flag "possible duplicate of X" in the merge queue. Never guess silently. Embeddings are deferred. |
| D20 | **Placement:** a new urban place links **only to the current node** with a default length from the district profile; a new room is a child of the current building. A provisional place **never links two canonical nodes** (prevents shortcuts and teleporting). It is usable immediately. |
| D21 | **Creation cap** (for example, 5 per conversation and 15 per day). Beyond the cap, a mention only raises salience. |
| D22 | **Outcomes:** *approve* (becomes canonical; history is immutable and past journeys are not recomputed) · *merge into* (becomes an alias; visits and episodes are transferred) · *discard* (tombstoned, not deleted; anyone currently there is **relocated to the parent node** with a recorded event). |
| D23 | **Who creates what:** user → canonical directly · companion → provisional · companion in her own home → rooms with lighter approval · calendar → provisional with `calendar` origin · user's home → changed only by the user. |
| D24 | **Merging interior graphs:** room-by-room mapping (matches / is new / discard), under the D22 rules. |

## Open questions requiring platform validation

- Does a silent `kin ask` exchange persist in the character's memory? If so,
  period summaries may duplicate or contradict it. The Kindroid integration is
  in alpha; this requires an authorized, authenticated test.
- What the platform adapter can observe to detect an active user.

## Consequences for the frontend contract

To be addressed after the engine contracts:

- Replace the single-connection `journey` (`connectionId`, `departedAt`,
  `earliestArrivalAt`) with `Journey` and its legs, mode and participants. This
  makes direction explicit and removes the zero-duration progress division.
- Add the user avatar, parked vehicles, commitments, provisional places and the
  merge queue to the snapshot.
- Load snapshots per level instead of the whole world.
- Moving the avatar and merge decisions are **writes**: the frontend stops being
  strictly read-only. That boundary change needs its own decision.
